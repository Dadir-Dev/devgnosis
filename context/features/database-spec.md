# Drizzle ORM + Neon PostgreSQL Setup

## Overview

Set up Drizzle ORM against the Neon PostgreSQL database, including the schema for the
DevGnosis data model, the auth tables managed by Better Auth, indexes/constraints, and the
versioned-migration workflow.

This supersedes the earlier Prisma version of this document. Prisma is **not** used in this
project; see `@context/coding-standards.md` → "Database: Neon PostgreSQL and Drizzle".

## Requirements

- Use Neon PostgreSQL (serverless).
- Use **Drizzle ORM** for all database access. Do not add Prisma (`prisma`, `@prisma/client`)
  anywhere in the project.
- Create the initial schema from the data models in `@context/project-overview.md`. The schema
  will evolve; treat this as the first reviewed migration, not a frozen design.
- Include the auth tables (Better Auth's `user`, `session`, `account`, `verification`), kept
  distinct from application profile/subscription data.
- Add appropriate indexes, unique constraints, `CHECK` constraints, and cascade deletes.
- Never use `drizzle-kit push` against a shared or production database. Always create and
  apply reviewed migrations.

## Environment and branch strategy

Neon branching is the isolation mechanism: a **development** branch for day-to-day work and a
**production** branch for live data. Migrations are always authored against the development
branch and promoted as the same SQL artifacts.

`drizzle-kit` (DDL) and the application runtime connect through different endpoints:

| Variable               | Endpoint                              | Used by                                            |
| ---------------------- | ------------------------------------- | -------------------------------------------------- |
| `DATABASE_URL`         | Neon branch, **direct** (non-pooler)  | `drizzle.config.ts` — `generate`, `migrate`, `check`, `studio`, seeds |
| `DATABASE_URL_POOLED`  | Neon branch, **pooled** (PgBouncer)   | The Next.js application at runtime                  |

Both point at the **same Neon branch** for a given environment. Each environment (local, CI,
preview, production) supplies its own values for these two names, so no code changes when
moving between the development and production branches. The existing `.env` already provides
both for the development branch.

Migrations use the direct endpoint because DDL and `drizzle-kit`'s session handling are not
pooler-friendly; the app uses the pooled endpoint to avoid connection exhaustion.

- Validate environment variables with Zod in a server-only module (for example
  `src/lib/env.ts`) and fail fast at startup when a required value is missing.
- `.gitignore` ignores `.env*`. To commit a `.env.example` template, add a `!.env.example`
  negation; never commit real credentials.

Package manager is **bun**.

```bash
# Tooling

```

- `@neondatabase/serverless`: Neon serverless driver (`neon-http` / `neon-serverless`).

Pin exact versions in `package.json` once installed.

## `drizzle.config.ts`

```ts
import "dotenv/config";
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  dialect: "postgresql",
  schema: "./src/db/schema/*",
  out: "./src/db/migrations",
  dbCredentials: {
    // Direct (non-pooled) endpoint of the current Neon branch.
    url: process.env.DATABASE_URL!,
  },
  strict: true,
  verbose: true,
});
```

- `drizzle-kit migrate` records applied migrations in `__drizzle_migrations` in the `drizzle`
  schema (the default; leave it as-is).
- Run configs with `bun x drizzle-kit …`; package scripts are defined below.

## Database client

The project needs interactive transactions for multi-step invariants (item + join rows,
idempotent webhook processing), so use the **WebSocket-based `neon-serverless`** driver, which
supports sessions and `db.transaction()`. `neon-http` supports only single statements and
non-interactive batches, so it is not the default.

```ts
// src/db/index.ts
import "server-only";

import { Pool, neonConfig } from "@neondatabase/serverless";
import { drizzle } from "drizzle-orm/neon-serverless";
import ws from "ws";

import * as schema from "./schema";

neonConfig.webSocketConstructor = ws;

// Cache the pool across dev hot reloads so connections are not leaked.
const globalForDb = globalThis as unknown as { pool?: Pool };

const pool =
  globalForDb.pool ??
  new Pool({ connectionString: process.env.DATABASE_URL_POOLED! });

if (process.env.NODE_ENV !== "production") {
  globalForDb.pool = pool;
}

export const db = drizzle({ client: pool, schema });
```

- Add `ws` (and optionally `bufferutil`) as a dependency: Node does not define a global
  `WebSocket`, and the Neon WebSocket driver requires one to be supplied.
- `import "server-only"` keeps the client out of any bundle that could reach the browser.
- If read latency on simple, non-transactional queries becomes a measured problem, add a
  separate `neon-http` client for those reads rather than adding a cache layer (Redis is not an
  MVP dependency).
- Close or reuse a single pool per process; do not construct `new Pool(...)` per request.

## Auth tables (Better Auth)

Better Auth owns `user`, `session`, `account`, and `verification`. Generate them with the
Better Auth CLI and commit the output; do not hand-write or hand-edit them beyond regeneration:

```bash
bun x auth@latest generate
```

- The adapter is configured with `provider: "pg"` and the Drizzle client:
  `database: drizzleAdapter(db, { provider: "pg", schema })`.
- Keep the generated tables in `src/db/schema/auth.ts` and re-export them from
  `src/db/schema/index.ts`.
- Better Auth generates `text` primary keys, so every `owner_id` / `user_id` foreign key in
  the application schema is `text` — not `uuid`.
- After generating, run `bun run db:generate` so the auth tables become part of the reviewed
  migration history like any other schema change.
- **Implemented command** (records the output path and forces the Drizzle/PostgreSQL generator):

  ```bash
  bun x auth@latest generate --config src/lib/auth.ts \
    --output src/db/schema/auth.ts --adapter drizzle --dialect postgresql -y
  ```

  This is wired up as `bun run auth:generate`.
- **Caveat — the CLI cannot load `server-only`:** because `src/lib/auth.ts` imports the Drizzle
  client, and `src/db/index.ts` / `src/lib/env.ts` import `server-only`, the CLI aborts with
  *"Please remove import 'server-only' from your auth config file temporarily."* Temporarily
  remove those two `import "server-only";` lines, run `auth:generate`, then restore them. (The
  generated auth tables use plain `timestamp`, not `timestamptz`; per this spec they are not
  hand-edited beyond regeneration.)

**Decision (confirmed — recorded in `@context/project-overview.md`):** the overview previously
described `users` as "auth-managed identity plus `plan`, `planStatus`, and Stripe IDs", while the
coding standards require Better Auth's managed tables to stay distinct from app profile data.
**Resolved:** generated auth tables stay auth-only, and app-owned profile/entitlement fields live
in a `user_profiles` table (see below). Better Auth's `additionalFields` on `user` was considered
and rejected. `@context/project-overview.md` was updated in the same change so the two documents
agree.

## Application schema

Conventions (see `@context/coding-standards.md`):

- `snake_case` table/column names in PostgreSQL, camelCase properties in TypeScript.
- `uuid` (`defaultRandom()`) primary keys; `text` for foreign keys to auth tables.
- `timestamptz` (`timestamp(..., { withTimezone: true })`) for all timestamps.
- Cascade deletes for records wholly owned by a user; `restrict` where a delete must be
  deliberate.
- Derive types from the schema instead of hand-maintaining shapes:
  `typeof items.$inferSelect` / `typeof items.$inferInsert`.
- Define relations in `relations.ts` and pass the whole schema to `drizzle()` so relational
  queries (`db.query.*`) work. Better Auth's joins feature expects those relations too.

### `item_types`

Seeded system types are stable and cannot be renamed or deleted; custom types are deferred
beyond the MVP but the ownership rules are represented in the schema.

```ts
// src/db/schema/item-types.ts
import { sql } from "drizzle-orm";
import {
  boolean, check, pgEnum, pgTable, timestamp, uniqueIndex, uuid, varchar,
} from "drizzle-orm/pg-core";

import { user } from "./auth";

export const contentKind = pgEnum("content_kind", ["text", "url", "file"]);

export const itemTypes = pgTable(
  "item_types",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    // Null for system types; set for owner-defined custom types.
    ownerId: text("owner_id").references(() => user.id, { onDelete: "cascade" }),
    key: varchar("key", { length: 40 }).notNull(),
    name: varchar("name", { length: 80 }).notNull(),
    icon: varchar("icon", { length: 60 }).notNull(),
    color: varchar("color", { length: 7 }).notNull(), // hex, e.g. #3B82F6
    contentKind: contentKind("content_kind").notNull(),
    isSystem: boolean("is_system").notNull().default(false),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    // System keys are globally unique.
    uniqueIndex("item_types_system_key_idx").on(t.key).where(sql`is_system`),
    // Custom type names are unique per owner.
    uniqueIndex("item_types_owner_name_idx")
      .on(t.ownerId, t.name)
      .where(sql`not is_system`),
    // A row is either a system type (no owner) or an owned custom type.
    check(
      "item_types_owner_chk",
      sql`(${t.isSystem} and ${t.ownerId} is null) or (not ${t.isSystem} and ${t.ownerId} is not null)`,
    ),
  ],
);
```

### `items`

```ts
// src/db/schema/items.ts
import { sql, type SQL } from "drizzle-orm";
import {
  bigint, boolean, check, customType, index, pgTable, text, timestamp, uuid, varchar,
} from "drizzle-orm/pg-core";

import { user } from "./auth";
import { itemTypes } from "./item-types";

const tsvector = customType<{ data: string }>({
  dataType: () => "tsvector",
});

export const items = pgTable(
  "items",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    ownerId: text("owner_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    itemTypeId: uuid("item_type_id")
      .notNull()
      .references(() => itemTypes.id, { onDelete: "restrict" }),
    title: varchar("title", { length: 160 }).notNull(),
    description: text("description"),

    // Exactly one payload is set: content (text) | url (link) | storage_key (file).
    content: text("content"),
    url: text("url"),
    storageKey: text("storage_key"),
    fileName: text("file_name"),
    mimeType: varchar("mime_type", { length: 255 }),
    fileSizeBytes: bigint("file_size_bytes", { mode: "number" }),

    language: varchar("language", { length: 80 }),
    isFavorite: boolean("is_favorite").notNull().default(false),
    isPinned: boolean("is_pinned").notNull().default(false),
    lastOpenedAt: timestamp("last_opened_at", { withTimezone: true }),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),

    searchVector: tsvector("search_vector").generatedAlwaysAs(
      (): SQL => sql`setweight(to_tsvector('english', coalesce(${items.title}, '')), 'A')
        || setweight(to_tsvector('english', coalesce(${items.description}, '')), 'B')
        || setweight(to_tsvector('english', coalesce(${items.content}, '')), 'C')`,
    ),
  },
  (t) => [
    index("items_owner_updated_idx").on(t.ownerId, t.updatedAt.desc()),
    index("items_owner_type_idx").on(t.ownerId, t.itemTypeId),
    index("items_owner_recent_idx").on(t.ownerId, t.lastOpenedAt.desc()),
    index("items_search_idx").using("gin", t.searchVector),

    // Storage-mode invariants (the per-type payload shape is enforced in Zod, because
    // content_kind lives on item_types and cannot be referenced by a CHECK here).
    check(
      "items_payload_exclusive_chk",
      sql`((${t.content} is not null)::int + (${t.url} is not null)::int + (${t.storageKey} is not null)::int) = 1`,
    ),
    check(
      "items_file_fields_chk",
      sql`${t.storageKey} is not null
        or (${t.fileName} is null and ${t.mimeType} is null and ${t.fileSizeBytes} is null)`,
    ),
    check(
      "items_file_metadata_chk",
      sql`${t.storageKey} is null
        or (${t.fileName} is not null and ${t.mimeType} is not null
            and ${t.fileSizeBytes} is not null and ${t.fileSizeBytes} > 0)`,
    ),
  ],
);
```

Notes:

- `content_kind` is intentionally **not** duplicated onto `items`. Per-type validation belongs
  in the Zod discriminated union for item content (`text` / `url` / `file`), per the coding
  standards' "enforce cross-table ownership invariants in a transaction/service layer". The
  `CHECK`s above cover everything derivable from a single row.
- The generated `search_vector` uses a fixed `'english'` configuration so the expression stays
  `IMMUTABLE` and can be persisted/indexed. Changing the expression later requires a migration
  that drops and re-adds the column, which rebuilds the GIN index — expect it in the search
  workstream, not incidentally.
- Deleting an item cascades its join rows but not the R2 object; object cleanup is a controlled
  workflow that runs alongside item deletion.

### `collections` and `item_collections`

```ts
// src/db/schema/collections.ts
import {
  boolean, index, pgTable, primaryKey, text, timestamp, uniqueIndex, uuid, varchar,
} from "drizzle-orm/pg-core";

import { user } from "./auth";
import { itemTypes } from "./item-types";
import { items } from "./items";

export const collections = pgTable(
  "collections",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    ownerId: text("owner_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    slug: varchar("slug", { length: 80 }).notNull(),
    name: varchar("name", { length: 120 }).notNull(),
    description: text("description"),
    isFavorite: boolean("is_favorite").notNull().default(false),
    defaultTypeId: uuid("default_type_id").references(() => itemTypes.id, {
      onDelete: "set null",
    }),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    uniqueIndex("collections_owner_slug_idx").on(t.ownerId, t.slug),
    index("collections_owner_updated_idx").on(t.ownerId, t.updatedAt.desc()),
  ],
);

export const itemCollections = pgTable(
  "item_collections",
  {
    itemId: uuid("item_id")
      .notNull()
      .references(() => items.id, { onDelete: "cascade" }),
    collectionId: uuid("collection_id")
      .notNull()
      .references(() => collections.id, { onDelete: "cascade" }),
    addedAt: timestamp("added_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    primaryKey({ columns: [t.itemId, t.collectionId] }),
    index("item_collections_collection_added_idx").on(t.collectionId, t.addedAt.desc()),
  ],
);
```

The slug is a locator only — never an authorization mechanism. Whether `collection_id` and
`item_id` belong to the same owner is a cross-row invariant enforced in the service layer
inside a transaction (a `CHECK` cannot see across tables).

### `tags` and `item_tags`

```ts
// src/db/schema/tags.ts
import {
  index, pgTable, primaryKey, text, timestamp, uniqueIndex, uuid, varchar,
} from "drizzle-orm/pg-core";

import { user } from "./auth";
import { items } from "./items";

export const tags = pgTable(
  "tags",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    ownerId: text("owner_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    name: varchar("name", { length: 60 }).notNull(),
    normalizedName: varchar("normalized_name", { length: 60 }).notNull(),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [uniqueIndex("tags_owner_normalized_name_idx").on(t.ownerId, t.normalizedName)],
);

export const itemTags = pgTable(
  "item_tags",
  {
    itemId: uuid("item_id")
      .notNull()
      .references(() => items.id, { onDelete: "cascade" }),
    tagId: uuid("tag_id")
      .notNull()
      .references(() => tags.id, { onDelete: "cascade" }),
  },

```

`normalized_name` is the lowercased/trimmed form produced by the server on write; it is what
uniqueness and lookups use.

### `user_profiles` and `subscriptions`

```ts
// src/db/schema/profiles.ts
import {
  boolean, index, pgTable, text, timestamp, uniqueIndex, uuid, varchar,
} from "drizzle-orm/pg-core";

import { user } from "./auth";

export const userProfiles = pgTable("user_profiles", {
  userId: text("user_id")
    .primaryKey()
    .references(() => user.id, { onDelete: "cascade" }),
  displayName: varchar("display_name", { length: 80 }),
  // Effective entitlement mirror; the authoritative billing state is `subscriptions`.
  plan: varchar("plan", { length: 20 }).notNull().default("free"),
  planStatus: varchar("plan_status", { length: 30 }).notNull().default("active"),
  stripeCustomerId: text("stripe_customer_id"),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
});

export const subscriptions = pgTable(
  "subscriptions",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    userId: text("user_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    provider: varchar("provider", { length: 20 }).notNull().default("stripe"),
    providerCustomerId: text("provider_customer_id").notNull(),
    providerSubscriptionId: text("provider_subscription_id").notNull(),
    plan: varchar("plan", { length: 20 }).notNull(),
    status: varchar("status", { length: 30 }).notNull(),
    currentPeriodEnd: timestamp("current_period_end", { withTimezone: true }),
    cancelAtPeriodEnd: boolean("cancel_at_period_end").notNull().default(false),
    lastWebhookAt: timestamp("last_webhook_at", { withTimezone: true }),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    uniqueIndex("subscriptions_provider_subscription_idx").on(
      t.provider,
      t.providerSubscriptionId,
    ),
    index("subscriptions_user_idx").on(t.userId),
  ],
);
```

Use `varchar` + application validation (not `pgEnum`) for `plan` and `status`: Stripe status
strings change over time and altering a Postgres enum is a migration-heavy operation.
`plan`/`planStatus` are derived from `subscriptions` (written idempotently by the webhook
handler); they are never the sole entitlement record, and there is no `isPro` boolean.

## Migration workflow

Scripts in `package.json` (bun):

| Script              | Command                              | Purpose                                      |
| ------------------- | ------------------------------------ | -------------------------------------------- |
| `db:generate`       | `drizzle-kit generate`               | Generate SQL + snapshot from the schema      |
| `db:migrate`        | `drizzle-kit migrate`                | Apply pending migrations to `DATABASE_URL`   |
| `db:check`          | `drizzle-kit check`                  | Detect conflicting/inconsistent migration history |
| `db:studio`         | `drizzle-kit studio`                 | Inspect the database                          |
| `db:seed`           | `bun run src/db/seed.ts`             | Idempotently seed system item types          |
| `auth:generate`     | `bun x auth@latest generate`         | Regenerate Better Auth tables                |

Rules:

1. **`db:push` is never used against a shared or production database.** Do not add a `db:push`
   script. `push` may only be pointed at a disposable throwaway branch, and only when explicitly
   specified.
2. Author changes against the development branch: edit `src/db/schema/*` → `bun run db:generate`
   → **read the generated SQL** → `bun run db:migrate`.
3. Migrations in `src/db/migrations` are append-only and immutable once shared or deployed.
   If a migration is wrong before it has been shared, fix the schema and regenerate rather than
   editing applied SQL.
4. The same migration files are promoted unchanged to staging and production. CI runs
   `bun run db:check` before deployment; production migration is a deliberate, gated step.
5. Never edit the database by hand. Any structural change becomes a migration.
6. When the Drizzle version changes, use `drizzle-kit up` to upgrade migration snapshots.

## Seeding system item types

The seven system types (Snippet, Prompt, Note, Command, Link, File, Image) with their icons,
colors, and `content_kind` must exist in every environment. Seeding must be deterministic and
idempotent — safe to run repeatedly and on every deploy:

- `src/db/seed.ts` upserts on the partial unique index over `key` where `is_system` is true.
  With Drizzle, the conflict target must match `item_types_system_key_idx`, including its
  predicate:

  ```ts
  await db
    .insert(itemTypes)
    .values(SYSTEM_ITEM_TYPES)
    .onConflictDoUpdate({
      target: itemTypes.key,
      targetWhere: sql`is_system`,
      set: {
        name: sql`excluded.name`,
        icon: sql`excluded.icon`,
        color: sql`excluded.color`,
        contentKind: sql`excluded.content_kind`,
        updatedAt: sql`now()`,
      },
    });
  ```
- Alternatively, express the seed as an append-only custom SQL migration.
- Do **not** use `drizzle-seed` for this: it generates randomised fake data for fixtures, not
  the fixed system catalog. It is a reasonable tool for local dev fixtures later.
- Uphold `is_system` in the service layer so end users cannot rename or delete system types;
  the schema represents custom ownership rules but no MVP UI or API exposes them.
